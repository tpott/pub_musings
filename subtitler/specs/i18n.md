# Internationalization (i18n) Specification

## Overview

Add language selection to the Settings page so users can view the website in their preferred language. Uses a zero-dependency approach with TypeScript translation modules and localStorage persistence.

## Approach

### No new dependencies

All i18n infrastructure is implemented with TypeScript modules and Astro's existing build system. No i18n libraries are added.

### URL structure

No URL-based locale routing (no `/en/`, `/es/` prefixes). Language is a user preference stored in localStorage, not a URL concern. This keeps the existing URL structure intact and avoids page restructuring.

### Translation architecture

```
frontend/src/i18n/
  config.ts          # Supported languages, default, helper functions
  en.ts              # English (default, canonical — all keys defined here)
  es.ts              # Spanish
  hi.ts              # Hindi
  fr.ts              # French
  cowboy.ts          # American Cowboy (English variant)
```

Each translation file exports a flat record of key-value pairs:

```typescript
// en.ts — the canonical file, all keys must exist here
export const en = {
  // Navigation
  'nav.login': 'Log in',
  'nav.signup': 'Sign up',
  'nav.logout': 'Log out',
  'nav.settings': 'Settings',
  'nav.upload': 'Upload',
  'nav.videos': 'My Videos',

  // Settings page
  'settings.title': 'Settings',
  'settings.tab.security': 'Security',
  'settings.tab.account': 'Account',
  'settings.tab.preferences': 'Preferences',
  'settings.language.label': 'Language',
  'settings.language.description': 'Choose your preferred language for the interface.',
  // ... etc
} as const;

export type TranslationKey = keyof typeof en;
```

Other language files implement `Partial<Record<TranslationKey, string>>`. Missing keys fall back to English.

```typescript
// cowboy.ts
import type { TranslationKey } from './en';

export const cowboy: Partial<Record<TranslationKey, string>> = {
  'nav.login': 'Mosey on in',
  'nav.signup': 'Sign up, partner',
  'nav.logout': 'Hit the dusty trail',
  'nav.settings': 'Outfit yer rig',
  'nav.upload': 'Wrangle a video',
  'nav.videos': 'My cattle',
  'settings.title': 'Outfit Yer Rig',
  'settings.tab.preferences': 'How I like it',
  'settings.language.label': 'Speak',
  'settings.language.description': 'Pick yer lingo, cowpoke.',
  // ... etc
};
```

### Config module

```typescript
// config.ts
import { en, type TranslationKey } from './en';
import { es } from './es';
import { hi } from './hi';
import { fr } from './fr';
import { cowboy } from './cowboy';

export const SUPPORTED_LANGUAGES = {
  en: 'English',
  es: 'Espa\u00f1ol',
  hi: '\u0939\u093f\u0928\u094d\u0926\u0940',
  fr: 'Fran\u00e7ais',
  cowboy: 'American Cowboy \ud83e\udd20',
} as const;

export type LanguageCode = keyof typeof SUPPORTED_LANGUAGES;
export const DEFAULT_LANGUAGE: LanguageCode = 'en';

const translations: Record<LanguageCode, Partial<Record<TranslationKey, string>>> = {
  en,
  es,
  hi,
  fr,
  cowboy,
};

/** Get the user's saved language preference, or the default. */
export function getLanguage(): LanguageCode {
  try {
    const saved = localStorage.getItem('subtitler:language');
    if (saved && saved in SUPPORTED_LANGUAGES) {
      return saved as LanguageCode;
    }
  } catch {
    // localStorage unavailable
  }
  return DEFAULT_LANGUAGE;
}

/** Save language preference. */
export function setLanguage(lang: LanguageCode): void {
  try {
    localStorage.setItem('subtitler:language', lang);
  } catch {
    console.error('Failed to save language preference');
  }
}

/** Translate a key. Falls back to English if not found in the target language. */
export function t(key: TranslationKey, lang?: LanguageCode): string {
  const effectiveLang = lang ?? getLanguage();
  return translations[effectiveLang]?.[key] ?? en[key] ?? key;
}
```

## Supported Languages

| Code | Name | Type | Notes |
|------|------|------|-------|
| `en` | English | Default | Canonical — all keys defined here |
| `es` | Espanol | Full translation | One of the most spoken languages globally |
| `hi` | Hindi | Full translation | Large internet user base |
| `fr` | Francais | Full translation | Widely spoken, good for testing RTL-unrelated i18n |
| `cowboy` | American Cowboy | English variant | Fun/novelty language for testing; stylized 19th-century cowboy English |

### Why these languages

- **Spanish, Hindi, French**: Cover 3 major language families (Romance, Indo-Aryan, Romance) with distinct scripts (Latin, Devanagari, Latin with accents). Good coverage for testing text length variations.
- **American Cowboy**: User-requested novelty language. Since it's English-based, it's easy to write translations. It also serves as a test harness — if the user sees untranslated English text while in Cowboy mode, that text is missing from the i18n system.

### Adding new languages

1. Create `frontend/src/i18n/{code}.ts`
2. Export a `Partial<Record<TranslationKey, string>>` with translations
3. Add to `SUPPORTED_LANGUAGES` and `translations` in `config.ts`
4. No other changes needed

## Language Selection UI

### Location

Settings page > Preferences tab, above the Bionic Reading toggle.

### UI design

```
Language
Choose your preferred language for the interface.

[English           v]   <-- <select> dropdown
```

The `<select>` shows language names in their native script (e.g., "Hindi" shows as "हिन्दी"). The currently selected language is stored in localStorage under `subtitler:language`.

When the user changes the language, the page reloads to apply translations.

## Implementation Strategy

### Phase 1: Foundation + Settings page

1. Create `frontend/src/i18n/` directory with `config.ts` and `en.ts`
2. Extract all hardcoded strings from `settings.astro` into `en.ts` (~120 keys)
3. Add language selector to Preferences tab
4. Create `cowboy.ts` with cowboy translations for Settings page
5. Create stub files for `es.ts`, `hi.ts`, `fr.ts` (can be filled in later)
6. Replace hardcoded strings in `settings.astro` with `t()` calls

### Phase 2: Navigation and shared components

1. Extract strings from navigation (`nav-auth.ts`), `FeedbackButton.astro`, `CookieConsent.astro`
2. Add translations

### Phase 3: Auth pages

1. Extract strings from login, register, forgot-password, reset-password, verify-email, magic-link pages

### Phase 4: Core pages

1. Extract strings from upload.astro (~200 keys) and videos.astro (~40 keys)
2. Extract strings from index.astro (~5 keys)

### String extraction pattern

For Astro template HTML:

```astro
---
import { t, getLanguage } from '../i18n/config';
const lang = getLanguage();
---
<!-- Before -->
<h2>Settings</h2>

<!-- After -->
<h2>{t('settings.title')}</h2>
```

For TypeScript in `<script>` tags or utility files:

```typescript
import { t } from '../i18n/config';

// Before
submitBtn.textContent = 'Send Feedback';

// After
submitBtn.textContent = t('feedback.submit');
```

**Important:** Astro renders HTML at build time, so `t()` calls in the template frontmatter use the server-side default language. For dynamic language switching, the `<script>` tag must update text content on page load using `t()` with the user's saved language from localStorage.

### Dynamic text update pattern

Since Astro is a static MPA, language switching requires updating DOM text after page load:

```typescript
// In <script> tag — runs client-side
import { t, getLanguage } from '../i18n/config';

const lang = getLanguage();
if (lang !== 'en') {
  // Update elements that have data-i18n attributes
  document.querySelectorAll('[data-i18n]').forEach(el => {
    const key = el.getAttribute('data-i18n');
    if (key) {
      el.textContent = t(key as TranslationKey);
    }
  });
}
```

HTML elements use `data-i18n` attributes:

```html
<h2 data-i18n="settings.title">Settings</h2>
```

The English text remains in the HTML as the default (good for SEO, no-JS fallback). The script replaces it with the translated text if a non-English language is selected.

## Detecting Untranslated Text

### Manual approach: Cowboy mode

1. Enable American Cowboy language in Settings
2. Browse the site
3. Any text that appears in normal English (not cowboy-styled) is missing from the i18n system

This is the primary detection method requested by the user.

### Automated approach: lint script

A lint script (`scripts/lint-i18n.sh` or integrated into `lint.sh`) detects untranslated text:

```bash
# Check that all keys in en.ts exist in cowboy.ts
# (cowboy is the test language — if a key is missing, it's untranslated)
```

Implementation:

```typescript
// scripts/check-i18n-coverage.ts (or .py)
// 1. Parse en.ts to extract all TranslationKey values
// 2. Parse each translation file to extract defined keys
// 3. Report missing keys per language
// 4. Exit non-zero if cowboy.ts has missing keys (cowboy = test language)
```

### Key naming convention

Keys follow a hierarchical dot-notation:

```
{page}.{section}.{element}
```

Examples:
- `nav.login` — navigation, login link
- `settings.tab.security` — settings page, security tab label
- `upload.dropzone.hint` — upload page, dropzone area, hint text
- `feedback.submit` — feedback button, submit text

## Testing Strategy

### Unit tests

1. **Translation coverage test** (`i18n/config.test.ts`):
   - Every key in `en.ts` exists (no typos in key names)
   - `t()` returns English text for unknown languages
   - `t()` returns cowboy text when cowboy language is set
   - `t()` falls back to English for missing keys in partial translations
   - `getLanguage()` returns default when localStorage is empty
   - `setLanguage()` persists to localStorage

2. **Translation completeness test**:
   - Cowboy has translations for all keys (cowboy = completeness test language)
   - No translation value is the same as the English value in cowboy (ensures it's actually translated, not copy-pasted)

### E2E tests

1. **Language selector test**:
   - Settings page shows language dropdown in Preferences tab
   - Changing language persists in localStorage
   - Page reload shows translated text

2. **Cowboy mode test**:
   - Set language to cowboy via localStorage
   - Navigate to Settings page
   - Verify tab labels are cowboy-styled (not English defaults)

### Regression tests

When adding new user-facing text to any page:
1. Add the English key to `en.ts`
2. Add the cowboy translation to `cowboy.ts`
3. The lint script catches missing keys

## Constraints

- **No new npm dependencies.** The entire i18n system uses TypeScript modules.
- **English is always the fallback.** Missing translations never show raw keys.
- **Page reload on language change.** No runtime re-rendering framework — Astro is a static MPA.
- **data-i18n attribute pattern** for DOM text that needs client-side translation.
- **Cowboy language must be complete** to serve as the untranslated text detector.
