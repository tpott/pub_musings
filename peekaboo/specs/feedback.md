# Feedback Feature Specification

## Overview

A simple feedback system that allows users to submit bug reports, feature requests, and general feedback from the main peekaboo interface.

## User Interface

### Floating Button
- Positioned in bottom-right corner
- Small, unobtrusive icon (speech bubble or question mark)
- Fixed position, always visible
- Hidden during active recording (to avoid distraction)
- Accessible: keyboard focusable, proper ARIA labels

### Feedback Modal
Opens when user clicks the floating button.

**Fields:**
1. **Type** (dropdown, required)
   - General Feedback
   - Bug Report
   - Feature Request

2. **Rating** (1-5 stars, optional)
   - Visual star picker
   - Keyboard accessible

3. **Message** (textarea, required)
   - Max 5000 characters
   - Placeholder: "Tell us what you think..."
   - Validation: non-empty after trim

4. **Submit button**
   - Disabled until form is valid
   - Shows loading state during submission
   - Success: closes modal with brief "Thanks!" message
   - Error: shows inline error message

**Behavior:**
- Closes on Escape key or clicking outside
- Focus trapped inside modal when open
- Returns focus to button when closed

## API Endpoint

### POST /api/feedback

**Request:**
```json
{
  "type": "general|bug|feature",
  "rating": 1-5 or null,
  "message": "string (max 5000 chars)",
  "context": {
    "session_id": "string",
    "concept_id": "string or null",
    "transcript": "string or null",
    "page_url": "string",
    "user_agent": "string"
  }
}
```

**Response (200 OK):**
```json
{
  "id": "feedback_abc123",
  "status": "ok"
}
```

**Error Responses:**
- 400 Bad Request: Invalid input (missing message, invalid type, etc.)
- 413 Payload Too Large: Message exceeds 5000 chars
- 429 Too Many Requests: Rate limited (5/min per IP)
- 500 Internal Server Error: Database error

**Rate Limiting:**
- 5 requests per minute per IP (separate from existing 10/min limits)
- Uses existing RateLimiter infrastructure

## Database Schema

```sql
CREATE TABLE IF NOT EXISTS feedback (
    id TEXT PRIMARY KEY,
    feedback_type TEXT NOT NULL,
    rating INTEGER,
    message TEXT NOT NULL,
    session_id TEXT NOT NULL,
    concept_id TEXT,
    transcript TEXT,
    page_url TEXT NOT NULL,
    user_agent TEXT,
    ip_address TEXT,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    status TEXT NOT NULL DEFAULT 'new'
);

CREATE INDEX IF NOT EXISTS idx_feedback_created_at ON feedback(created_at);
CREATE INDEX IF NOT EXISTS idx_feedback_status ON feedback(status);
```

**Fields:**
- `id`: UUID v4 generated by backend
- `feedback_type`: "general", "bug", or "feature"
- `rating`: 1-5 or NULL
- `message`: User's feedback text
- `session_id`: Anonymous session tracking (from localStorage)
- `concept_id`: Which animal was last shown (optional context)
- `transcript`: Last voice command (optional context)
- `page_url`: Always "/" for peekaboo
- `user_agent`: Browser info for debugging
- `ip_address`: For abuse tracking (not displayed to user)
- `created_at`: Timestamp
- `status`: "new", "read", "resolved" (for future admin use)

### Session ID Management
- Generate UUID v4 on first visit
- Store in localStorage as `peekaboo_session_id`
- Include in all feedback submissions

## Context Capture

The feedback submission should capture current app context:

1. **session_id**: From localStorage (generated on first visit)
2. **concept_id**: Last animal shown (if any) - from PeekabooFlow state
3. **transcript**: Last recognized speech (if any) - from transcript display
4. **page_url**: `window.location.href`
5. **user_agent**: `navigator.userAgent`

## Implementation Notes

### Backend
- Generate feedback ID with `crypto/rand` UUID v4
- Validate all input server-side
- Use `http.MaxBytesReader` to limit body size (8KB max)
- Log feedback submissions at INFO level
- Store IP address but don't include in response

### Frontend
- Hide feedback button during `recording` state
- Show button during `idle`, `processing`, `media`, `error` states
- Capture context at modal open time (not submit time)
- Clear form after successful submission

### Testing
- Backend: test validation, rate limiting, database insert
- Frontend: test modal open/close, form validation, submission
- E2E: test full flow with mocked API
